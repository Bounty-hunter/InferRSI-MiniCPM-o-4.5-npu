# RSI 与六层 profiling：问题、方案及实测增益

本文仅展开最后r296–r306这段。[完整优化历程](optimization-journey.zh-CN.md)从早期NPU迁移、RSI知识库迭代、
profiling＋自主策略讲到这一批；[全账本](optimization-ledger-npu.zh-CN.md)保留所有可核验历史实验及负结果。

日期：2026-11-02；硬件：每服务一张 Ascend 910B1（A2）。**以均值为主要指标，同时保留 P99。**
当前代码提供 r305 实验配置，未通过最终冻结语音质量门。文中的“改善”均为工程测量点，不等于冻结验证器验收。

## 两种比较分别回答什么

1. **独立引擎 vs vLLM-Omni**：回答用户使用这两套已测配置时，TTFP/RTF/request/s 分别差多少。
2. **r292 vs r305**：回答本次六层 profiling 指导的十轮优化后，在相同引擎配置下额外改变多少。

第二组不是“开 profiler 就自动加速”，也不是对 profiling 方法本身做过随机/隔离因果实验。两组收益不能相加。

## RSI 找到的核心问题

首音频依赖首文本。主机账本显示，Thinker prefill完成后到首文本chunk的等待，在低并发仍占重要比例。
独立诊断服务C2/C4/C8该区间由493.8/830.6/1420.8ms降到232.5/335.9/551.7ms。
它包含交错计算和等待，不能称为独占Thinker内核时间；诊断hooks与native性能服务分开，不拿插桩点替代正式计时。
emit→客户端均值仅约2–4ms，因此当前直接重写C++/Rust HTTP前端不能解释主要首包差距。

r305采用通用prompt-lookup：用本请求已生成2–4gram在prompt里找后继候选，最多8个token；原Thinker对整个因果块验证，
接受匹配前缀以及原模型的首个不匹配/bonus预测，截断未接受KV，保持原文本chunk边界、EOS、普通解码与容量回退。
没有数据集ID分支、预置答案、额外draft模型，也没有相对r292减少Flow步数、降低精度或改变chunk。
累计242次验证、3121个候选token、2223个匹配接受（71.23%，含三个档位warmup），KV容量回退0次。
减少的是串行解码/主机往返次数；被拒绝draft仍消耗计算，不保证所有场景有收益。

## 六层分别看到了什么

L0是额外的测量冻结层，L1–L6才是这里的“六层”；不是六个可相加的优化百分比。
借鉴[PR #9236](https://github.com/vllm-project/vllm-omni/pull/9236)冻结head174f306a00355b4d538e3015bf54cafd171d79a4的思路，
用NPUGraph/msprof/CANN对应NPU，未照搬CUDA/Nsight的提速数字。

| 层 | 实际发现 | 引导的实验与结果 |
|---|---|---|
| L0 测量合同 | RTF包含TTFP；生成时长也在分母；零HTTP错误不等于质量通过 | 固定模型、请求、客户端、chunk和引擎内部精度步数；native与profiling分服务 |
| L1 流水线时序 | 首文本等待占主导；HTTP emit后成本约2–4ms | r305减少串行Thinker轮次；C8诊断该区间1420.8→551.7ms |
| L2 图覆盖、调度及间隙 | C32有374/390纯decode分组超过graph8；整批T2W交付屏障；设备选中工作busy union61.86% | r297/298大图、r299分组提前交付、r303 EDF；均值与尾部有权衡，不能统一纳入 |
| L3 工作图与不变量 | Transpose/TransData/Cast占累计算子时长29.586%；固定timestep调制重复 | r304移出AdaLN常量表，没有稳定E2E增益；布局转换的具体owner仍需验证 |
| L4 算子与计数器 | 有797175行算子人口，MatMul/布局/归一化等；无matched-shape最优参考 | 避免把计数器当全局MFU，未宣称已接近硬件极限或盲目替换所有GEMM |
| L5 传输与所有权 | vocoder .cpu() 44次，主机观察均值53.285ms，包含设备等待 | r306 NPU pinned-buffer/event/锁外消费；首试API错误修复为r306b，仍无稳定E2E收益 |
| L6 组件评估与验收 | 单项更快可能移动等待或恶化续包/P99 | 原生三指标、源码绑定、错误率、开发parity、speech gate分开；保留失败及回退，不以少数span判定获益 |

证据：[设备分析](../evidence/20261102-r305/profiling/npu-analysis.json)、[主机分析](../evidence/20261102-r305/profiling/host-analysis.json)、
[图覆盖](../evidence/20261102-r305/profiling/graph-coverage-analysis.json)。
其中38.14%的设备区间未被选中kernel/copy覆盖，不等于可回收38.14%，29.586%的算子时间也不是E2E收益。
每轮有独立host/锁/capture/客户端chunk诊断；没有每轮重新采全量msprof或补齐全部Python→CANN关联。

## 剩余瓶颈与精度状态

r305 C4/C8最慢诊断请求与Euler/HiFT首次形状捕获相交约1.57/1.72秒。
这是主机区间重叠，不是native同一P99请求的独占关键路径，更不是保证可回收的1.7秒。
[逐请求捕获证据](../evidence/20261102-r305/profiling/tail-capture-analysis.json)支持继续研究有界媒体图初始化；这项额外实验尚未执行。
上游文本等待减少后，Talker/Flow窗口供给及首次capture成为更明显的残余成本，尚未达到已证明的性能极限。

开发16条C8：Thinker文本与token均16/16一致，codec token 0/16一致。
冻结WER/SIM/UTMOS等speech gate仍NOT_RUN，原评分服务连接关闭，不能用文本一致或零请求错误替代质量验收。
因此r305是实验候选。现有默认JSON不变，新增`ascend_r305_experimental`显式选择；prompt lookup默认0关闭。
保留公共server既有可选CPU affinity功能，其余engine文件与实测r305相同；发布树不是新跑的一轮计时。
[source manifest](../evidence/20261102-r305/source-manifest.json)提供实测hash、差异说明和精确复现方法。
