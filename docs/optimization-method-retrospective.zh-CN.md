# 优化方法复盘与探索效率审计

整理于 2026-11-03，覆盖统一官方 benchmark 后的 r182–r351，并回看前置 NPU 阶段的记录边界。本文分析这次 agent 驱动的执行过程，核对方案数量、未保留的原因，以及 profiling 为什么较晚才转化为较大收益。[完整账本](optimization-ledger-npu.zh-CN.md) · [机器可读审计](data/optimization-retrospective.json)

**RSI 本来就包含 profiling。本次早期实践的缺口在有效 trace、关键路径归因、候选命中预检和实验优先级。** 后续提示词使分析更聚焦于完整请求依赖，但现有记录没有隔离比较提示词或方法本身。6层profiling 诊断之后仍有大量未保留方案，当前也没有全局最优证明。

## 1. 总共多少轮，应当如何计数

### 先区分三个分母

| 分母 | 可以回答什么 | 本次情况 |
|---|---|---|
| 作业/证据主编号 | 有多少工作项在账本或后段活动中单列 | r182–r351 有 170 个编号位置，165 个有单列记录 |
| 原始算法方案轮 | 当时明确声明的新候选，排除控制、复测和错误重试 | r297–r306 共 10 轮，r307–r309 共 3 轮，r312–r351 共 40 轮，合计 53 轮 |
| 人工回溯方案组 | 将早期实现、修复、验证和复测归到明确方案下 | 前两阶段可重建 10 组和 32 组，连同后段共 95 条方案记录 |

早期 r203/r205/r209/r211/r213 没有独立正式候选记录。r240–r295 的 56 个主编号展开后有 66 个证据 ID，增加项包括 `b/c` 修复与复测。r296 是诊断，r310/r311 是确认与控制。前置 r32–r181 的归档不完整，因此**整个项目的精确算法运行总数无法从当前证据恢复**。不能用最大编号 351 代替总轮数，也不能将 165 个工作项全部算作新优化。[编号核对与源行哈希](data/optimization-retrospective.json) · [原账本](optimization-ledger-npu.zh-CN.md)

### 按公开归并规则核算方案

前两阶段把同一机制的正确性修复、parity、质量筛查和复测归为一组。更换性能策略或压力阈值时另列一组。例如 Talker 完整块的状态修复与复测归为一组，prefix 的 active8、active12、live12、live9 则分别列组。CFM 分解消融归入其后实际跟进的 full、packed-only、hybrid 路线，子算子探针不再拆成算法轮。附录公开全部人工划分。[分类代码](../tools/audit_optimization_retrospective.py)

| 阶段 | 方案数及口径 | 当前实验链保留/继承的方案节点 | 未作为独立方案保留 | 未保留占比 |
|---|---:|---:|---:|---:|
| RSI 知识适配为主，r182–r239 | 10 组，人工回溯 | 3 | 7 | 70.0% |
| profiling＋自主策略，r240–r295 | 32 组，人工回溯 | 4 | 28 | 87.5% |
| 6层profiling 诊断后，r297–r306 | 10 轮，原始记录 | 1 | 9 | 90.0% |
| owner 预热跟进，r307–r309 | 3 轮，原始记录 | 1 | 2 | 66.7% |
| 持续优化，r312–r351 | 40 轮，原始记录 | 2 | 38 | 95.0% |
| 本文回溯清单合计 | 95 条 | 11 | 84 | 88.4% |

**95 是本文人工归并后的清单数量。它与后段有明确合同的 53 轮分别保留，不能用 95 宣称恢复了全历史精确算法轮数。** 早期对大路线的归并较粗，后期包含细参数与组合消融，所以表中比例也不适合直接比较方法优劣。

“保留”表示当前 r337 实验配置继承了对应机制或父配置节点。它不证明该项独立改善全部指标。例如公平 gate 和首音频优先仍在配置中，但 r292 匹配复测在 C8/C32 回退。11 个节点也有继承、扩展及组合关系，不能视作 11 个独立可相加的收益。

“未保留”覆盖性能回退、收益不明确、数值/质量失败、运行失败、被扩展版本替代以及尚未完成验证。下文把这些情况分开。“84 次完全没价值”无法由这些记录支持。r307 的 owner 预热后来由 r309 扩展，r319 的 host 长度思路后来进入 r337，都是需要保留的反例。

## 2. RSI 确实已经有 profiling，差别出在哪里

InferRSI 的当前固定源码明确写了 `Profile first`，并说明由人或 coding agent 驱动 profiling 与代码修改，workbench 运行和评估外部 benchmark/validation 命令。其 Ascend 技能同时覆盖单算子及系统级分析。因此，工具能力中存在 profiling，并不保证每次执行都获得可用证据、正确确定优先级并完成反馈。这里引用当前框架合同来解释职责，历史执行情况仍由本项目账本证明。[InferRSI README 固定版本](https://github.com/InferMatrixLab/InferRSI/blob/a1ee3266466194c16f4e2159ab845b758ed9561b/README.md) · [Ascend 系统分析](https://github.com/InferMatrixLab/InferRSI/blob/a1ee3266466194c16f4e2159ab845b758ed9561b/src/inferrsi/data/skill_library/hardware/ascend/ascend-performance-analysis/SKILL.md)

本项目早期已经尝试 profiling。r188/r189/r190 的完整关联采集未形成可靠结果，r219 的最小 Flow profiler 仍 exit139。r195 有阶段计时，但 Thinker、Talker、Flow 的累计时间存在重叠，不能直接相加得到关键路径。直到 r277 的最小探针确认 `with_stack=True` 会在停止采集时崩溃，才转为无原生栈事件加补充 Python 采样，r278/r279 获得可用关联与轻量计数。[早期采集与 r277–r279](optimization-ledger-npu.zh-CN.md)

| 能力环节 | 当时实际不足 | 对搜索的影响 |
|---|---|---|
| 采到可用数据 | 完整 trace 多次异常，部分阶段仅有累计时间 | 候选更多依赖局部机制与源码推测 |
| 解释请求关键路径 | host span 包含设备等待、锁和交错执行 | 大耗时函数容易被当作可直接回收的成本 |
| 验证实际命中 | 某些图路径完成微测，但实际服务旁路 | benchmark 测到了负载波动，候选机制却未执行 |
| 将证据变成优先级 | 已看到首文本慢，仍花较多回合在图桶、前缀阈值和小算子 | 较晚才尝试减少串行文本生成工作 |
| 验证净收益 | 局部更快、初筛更快与完整跨档结果不一致 | 增加复测，部分早期收益被撤回 |

这些环节的执行质量限制了收敛速度。现有记录也没有完整证明每一轮都由统一的自动 RSI 搜索与反馈策略生成，所以本文将结论限定到这次 agent 驱动的实践。

## 3. 第一阶段为何没有直接优化到最优

### 目标与可比较基线在过程中重新固定

前置 r153 曾通过旧 K=10 验证器的性能门，使用 TTFA p50 和 frames/s，speech 尚未评分。随后用户指定官方 CI benchmark、主要看 TTFP mean/RTF/request/s，Omni 对照也更新到新的代码。旧协议中的性能通过不能证明新目标已优化到最优。跨日期端点同时包含执行改动、测量合同和运行波动，需要与当期匹配控制分别读取。[旧门与官方 CLI 迁移](optimization-journey.zh-CN.md)

### 知识提供机制，适配条件需要重新发现

graph batching、state ownership、固定条件复用和融合知识，对应到 MiniCPM-o 后仍需要解决真实的 dtype、batch、物理 KV 页、EOS、文本 chunk 交接和 CANN 图约束。知识库中的相似模型收益无法给出本模型每个 shape 的性能与数值结果。

例如 full Talker 块不是把十次调用包进图就完成。r202/r204/r210 的整模型差异，后来通过 condition hash 和 cohort 轨迹发现已经在进入 Talker 前产生。r214 对齐完整 cohort 后才通过严格模型验证，r215 才有可用服务收益。这一串工作包括正确性建设，不能全部记成性能方向无效。[r198–r215](optimization-ledger-npu.zh-CN.md)

### 局部指标多次无法预测端到端结果

| 例子 | 局部证据 | 最终问题 |
|---|---|---|
| 恒等 gather 消除，r191–r193 | 500 次约 59.4→11.0 ms，状态检查通过 | 服务吞吐在三档回退 |
| causal Conv1d 改窗口 GEMM，r221 | 数值/cache 检查通过 | 常见 C8 shape 反而慢 8%–12% |
| Thinker full 融合，r222–r226 | 部分性能和文本检查有利 | UTMOS/SIM 超出冻结容差 |
| packed-only CFM，r230–r237 | 局部图 replay 约快 15.6%，小型质量筛查通过 | C8 正式服务 52/128 请求失败 |

因此 10 组回溯路线中保留 K10 完整块、Talker Add+RMS 和 hybrid CFM 三组，其余七组没有独立保留。前三组也只是阶段性实验选择。该阶段 C8 吞吐从 r187 的 1.6063 到 r239 的 1.7500 request/s，端点观测约提高 8.94%，仍落后本次最新 Omni 的 1.9637 request/s。[阶段数据](data/optimization-journey.json) · [当前固定参考](current-results.md)

### 我当时可以更早做好的部分

完整 profiler 接连失败后，应该更早使用最小探针拆出采集问题，并建立低扰动阶段标记、真实 shape 和命中计数。候选排序也应该更早引入请求依赖，先估计目标开销在首音频路径上的份额，再决定是否值得做一个算子原型。现有证据支持这类执行顺序存在改进空间。

## 4. 为什么 profiling＋自主决策能够找到提升

### 新的方案选择开始使用实际流量结构

后续分析把计时与 shape、调度路径、请求压力及状态所有权结合起来，得到具体的条件式方案。

| 证据 | 推导出的策略 | 结果与边界 |
|---|---|---|
| Talker 实际存在未覆盖 cohort，全部精确桶又损害 C4 | 排除 row3，选择 1/2/4/5/6/7/8，大组 8+3 改 7+4 | r247 相对修改前 C8 吞吐 +9.59%，C16 +27.10% |
| 公共前缀重复计算，但常开破坏低并发调度 | 用 live-request 压力门控 prefix，最终 min_live=9 | 保留条件路径，当前 C1/C2/C4/C8 无命中收益可归因 |
| capture writer 长期等待，新的 reader 持续进入 | writer-aware gate | writer 等待减少，但等待向 reader 转移 |
| 首窗与续窗混排 | 稳定排序首音频窗口 | 初筛有利，匹配 C8/C32 仍回退 |

“自主决策”在这里体现为根据具体证据设计路由、阈值、生命周期和反例实验，仍使用知识库的图与状态管理原则。用户提示词改变了搜索重点，现有数据没有分离出提示词自身的因果效果。[阶段历程](optimization-journey.zh-CN.md)

### 这一阶段仍然有很多未保留探索

按本文人工规则为 32 组，四个机制节点在当前实验链保留，28 组没有独立保留。其中 r275/r276 的路由修复缺少正式服务结果，其余包含回退、未命中、收益不足和未通过跨档确认。详细分组见附录。

这里有一组明确可以改进的实验顺序。r266、r268、r270、r274 的 Thinker block 正式服务 replay 为零，r272 也只有一次。r275 才定位到低压力 prefix 旁路阻止 block 执行。**先证明短服务探针的 replay 非零，再跑完整 benchmark，至少能避免这四次零命中的服务实验过早进入性能阶段。** 这不需要再增加一个更复杂的 profiler。[Thinker block 逐轮记录](optimization-ledger-npu.zh-CN.md)

还需要保留一个负向事实。r239→r292 的跨日期 C8 端点吞吐约提高 8.68%，但最后 r295 的匹配比较中，r292 相对当期 r258 控制的 C8 吞吐回退 3.35%，C32 回退 6.07%。因此不能只用较早端点宣传这一批调度改动全面成功。[匹配原始数据](../evidence/optimization-journey/r295-matched-comparison.json)

## 5. 6层profiling 诊断为什么还能找到新点

### 首文本慢其实已经被看到过

r242 就记录到 C16 相对 C4 的新增首包等待中，65.56% 落在 prefill→首文本块。r279 的轻量时间线也把 Thinker prefill＋首文本块列为主要组成。因此，“之前没有发现首文本慢”与账本不符。

当时分析还重点覆盖 C16/C32，后期用户更关注 C2/C4/C8 的均值，优先研究的压力区间随之改变。高压力 prefix 和图覆盖曾有对应收益，不能把全部早期选择都归为走错方向。与此同时，已知首文本信号确实给更早研究串行工作量提供了依据。

**较晚完成的是把这个慢区间与任务中的重复工作联系起来。** 朗读内容已在当前请求 prompt 中，逐 token 再生成它仍形成串行依赖。r305 用 prompt 中的后继提议作为 draft，原 Thinker 做因果块验证，并截断未采用 KV，从而减少串行生成轮次。这个思路在 r242 后就有研究条件，我当时没有尽早把它放到图桶、prefix 阈值等方案之前。[首包分段与早期选择](optimization-journey.zh-CN.md) · [prompt-lookup 实现图示](adopted-optimizations.zh-CN.md)

### 后来的诊断将哪些证据连接起来

| 视角 | 之前已有的局部信息 | 后来加入的约束或关联 |
|---|---|---|
| 请求流水线 | 哪个阶段长 | 首音频究竟被哪条依赖阻塞，低并发是否仍存在 |
| 图与调度 | 图可运行、微测更快 | 真实行数覆盖、replay 命中、捕获冷启动和队列等待 |
| 工作冗余 | 某类算子占比高 | 哪些工作可以减少，哪些条件可复用，哪些是算法串行轮数 |
| 算子与计数器 | 内核人口和设备占用 | 与具体 shape 和工作量对应，保留未覆盖区间的未知性 |
| 拷贝与所有权 | `.cpu()` 的 host span 长 | 区分复制、设备等待、scratch 生命周期及输出交付依赖 |
| 组件与服务验收 | 微测或单档改善 | native 全档、尾部、播放连续性、错误及质量分别核对 |

L0 还冻结模型、请求、客户端和计时边界。6层profiling 诊断为这些证据建立了检查结构，实际采集仍使用 NPU 工具链。它没有创造一个保证发现新优化的算法，也没有要求每轮重新采集全量 msprof。[6层证据及覆盖限制](rsi-profiling-20261102.zh-CN.md)

### 真正得到的大收益来自减少串行工作

r305 相对当期同配置 r292 控制，C2/C4/C8 的 mean TTFP 分别降低 22.32%/25.60%/32.03%，request/s 分别提高 16.92%/15.43%/28.39%。C8 诊断区间 prefill→首文本从 1420.8 缩短到 551.7 ms。该区间包含等待及交错执行，不能将全部差值当作独占 Thinker 内核时间。[r305 数据](data/ascend-r305-20261102.json)

这也说明早期搜索重点的限制。图化主要压缩已有工作周围的发射成本，prompt-lookup 则在本朗读任务上减少串行轮次。定位到了慢函数之后，还需要提出能够改变其依赖或工作量的方案。

后续知识 readset 中也包含 speculative verification budget 等机制。现有材料没有证明早期知识库缺少相关思路，或者某个检索结果直接导致 r305。可核验的贡献是把这类机制适配到当前 prompt、文本 chunk、原 Thinker 验证和 KV 生命周期，并用服务数据确认。[后续知识读取记录](../evidence/20261103-r337/campaign/knowledge-readset.json)

## 6. 六层之后的十轮有多少无效

原始记录为 10 轮，仅 r305 作为新的性能方案进入当前实验链，九轮没有独立保留。但九轮内部的结果并不相同。

| 结果类型 | 轮次 | 数量 | 未采用原因 |
|---|---|---:|---|
| 有局部/部分均值改善，资格未闭合 | r297/r298/r299/r302/r303 | 5 | 缺稳定确认、P99/播放连续性权衡、作用仅在高并发或增量过小 |
| 对 parent 的原生结果回退 | r300/r301/r304 | 3 | 更小图、预热或常量表改动未转为服务收益 |
| 低并发无一致收益 | r306，修复为 r306b | 1 | 首次 API 错误修复后，三档结果仍混合 |
| 保留的重点方案 | r305 | 1 | prompt-lookup 及原模型验证，仍待完整 speech gate |

所以六层之后也有 **9/10 未保留**。这批较大收益来自一个命中主要串行依赖的方案，证据不足以证明六层方法提高了候选保留率。[十轮逐项结果](rsi-profiling-20261102.zh-CN.md)

## 7. 十轮与四十轮之间还有三项 owner 跟进

这段不能漏算，也不应混入后来的 40 轮。

| 方案 | 结果 |
|---|---|
| r307，实际音频 worker/stream 上的窄范围媒体预热 | 基础机制由扩展版继承，独立窄配置被替代 |
| r308，去掉 LM-head 后 FP32 cast | 算子检查通过，服务没有一致收益 |
| r309，扩展到续包、tail 及 prompt setup shape | 进入当前实验链，r310/r311 用于确认与控制 |

这里新的可行动信息是**首次 capture 的实际 owner、stream 与缺失 shape**。此前“预热”这个方向已经试过，但只改变时机、未对齐执行者与覆盖范围，无法保证移走实际服务中的捕获。r309 的 C8 增量吞吐较小，初筛约 +0.88%，反序对照约 +0.72%，仍应保留波动边界。[owner 跟进及全部原值](../evidence/20261103-r337/followup/六层profiling继续优化-r307-r309.md)

## 8. 最后持续四十轮究竟留下了什么

| 初筛状态 | 数量 | 占 40 轮 |
|---|---:|---:|
| 无一致收益或证据不足 | 29 | 72.5% |

| 算子/框架拒绝或运行失败 | 7 | 17.5% |

### 当前链的两个新增配置节点

```text
control309
    └── r320  当前进程 12 Cube / 24 Vector
          └── r337  增加可信 host 累计 query 长度复用

r319 曾单独测试 host 长度，思路在 r337 复用
```

## 9. 为什么四十轮仍有这么多未保留

### 剩余热点中，小改动较多，服务净收益较小

r305 已减少首文本串行轮次，owner 预热又移走部分首用成本。之后的 token 上传合并、页号缓存、mask 缓存、少量 cast、RoPE/RMS 小链等，处理的是剩余开销。即使某段能够明显变快，它占请求关键路径的份额也可能很小。现有记录未给每项候选建立可靠的收益上界，这使若干合理的小原型进入了完整三档实验。

r341 就提供了具体反例。C++ 小算子执行链在 12 种独立 case、重复检查及 16 条 Thinker 比较中可通过，但没有获得三档一致收益。CPU 采样显示主机引擎线程繁忙，仍不能据此把耗时全部解释为 Python 计算，再预期换语言必然提速。[CPU、语言实验及采样限制](../evidence/20261103-r337/campaign/CPU瓶颈与语言选择.md)

### 实际合批轨迹使方向不单调

r315 合并验证在初筛有利，反序确认 C8 仍有改善，但 C4 RTF 回退约 3.00%、吞吐回退约 3.33%。更长 draft、更多精确行数桶、较小图拆分，也会同时改变 padding、设备批效率、等待和图内存。减少一个局部成本无法保证所有并发都更快。[r315 反序确认](../evidence/20261103-r337/campaign/confirmation1-analysis.json)

### 锁等待指出了依赖，删除依赖需要新的安全实现

private prompt Flow 试图减少共享 scratch 等待，但原生服务崩溃。异步 PCM、独立 arena 和更多并行路径都需要维护 capture、输入重绑、cache 与缓冲生命周期。合理的 profile 线索仍可能遇到实现或工具链边界。7 次失败中至少一部分可以由更早的并发 capture/replay 与资源最小探针降低成本，但现有材料不足以认定七次全部可提前避免。

### 初筛波动与确认粒度仍限制判断

r343 的音频 stream 核配额初筛较好，最终 C8 的 RTF/吞吐范围跨零。r320 首筛 C8 回退，A/B/A 却显示有利。请求数增多能减少部分请求内抽样波动，但相同服务启动、capture 状态和资源竞争带来的相关性仍然存在。当前少量服务级重复也无法为所有 1% 左右的差值给出可靠的长期结论。[最终确认](../evidence/20261103-r337/campaign/final-confirmation-summary.json)

### 搜索仍包含细变体和组合，负结果复用需要加强

host metadata/mask、图桶、拆分和预热在多个阶段重复出现。不同版本下重新验证可能合理，但需要明确新增证据、实现差异和预期改变的失败条件。若只因“再试一种参数”就再次进入完整 benchmark，会增加低信息量回合。当前记录保留了负结果，但没有证据证明每次候选提出都经过了系统化的重复路线排查。

**这四十轮证明继续探索仍能找到增量，也显示筛选和实验预算分配还有改进空间。** 本次收尾来自 40 轮上限，尚未完成多机制局部平台验证和完整质量验收，更无法推出达到全局最优。[收尾审计](../evidence/20261103-r337/campaign/finalization.json)

## 10. 这次流程最应改进的地方

这些改进针对上述可核验问题，本文仅整理流程要求。

| 应前置的检查 | 对应的已发生问题 | 完整性能实验前需要的证据 |
|---|---|---|
| 采集器最小自检 | r188–r190/r219 多次异常 | 能导出完整事件，明确栈/计数器限制 |
| 候选命中短探针 | 四个零 replay 的 block 服务实验 | 真请求路径命中、replay 次数、fallback 原因 |
| 请求依赖与收益粗估 | 大量小算子候选，prompt-lookup 较晚出现 | 关键等待、可减工作及覆盖请求比例 |
| 启动/稳态与实际 owner 分开 | 旧预热后服务仍首次 capture | owner、stream、shape、初始化成本与真实 replay |
| 最小并发稳定性探针 | packed-only、私有 Flow、cache 实验失败 | 多 shape 交替、重绑、EOS、释放与 capture/replay |
| 父版本、目标并发和负结果检索 | 阈值、mask、图桶路线多次重试 | 新假设相对旧失败到底改变了什么 |
| 新鲜控制与反序确认 | 初筛收益撤回、r320/r343 的反例 | 独立 native 服务、输出工作量、正反序原值 |
| 单项与组合分开归因 | 核配额＋host 长度组合 | 组合可保留，但单项贡献保留未知 |

RSI 的工作台、知识与证据约束可以支持这套流程，agent 仍须执行这些检查并据结果更新优先级。单纯增加“profiling”“自主决策”或“六层”的词语，无法替代命中预检、依赖分析和受控验证。
